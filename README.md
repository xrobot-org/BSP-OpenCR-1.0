# BSP-OpenCR-1.0

OpenCR 1.0（STM32F746ZGTx）的 LibXR / XRobot BSP / LibXR and XRobot BSP for OpenCR 1.0 (STM32F746ZGTx)

## 1. 板子与平台 / Board and Platform

OpenCR 1.0 使用 STM32F746ZGTx，系统为 FreeRTOS，终端通过 USB CDC（`usb_otg_fs_cdc`）提供。外设由 CubeMX 工程 `OpenCR1.0.ioc` 配置，`libxr` 命令生成入口源文件 `User/app_main.cpp`，并在其中用 `XR_REGISTER` 完成硬件注册。配置中的硬件名即这些注册名，例如 `LED1`、`IMU_CS`、`IMU_INT`、`spi1`、`can2`、`pwm_buzzer`、`database`、`ramfs`。其中 `usb_otg_fs_cdc`、`ramfs`、`pwm_buzzer` 以及 USB DFU 运行时和终端由 `User Code Begin 3` 区域中的手写代码创建并注册，其余由 `libxr` 命令生成；`User/libxr_config.yaml` 中 `USB.usb_otg_fs.enable` 为 false。数据库 `database` 由 `User/libxr_config.yaml` 中 `database` 的设置生成，使用 Flash 末尾的扇区 6 和 7（0x08080000 起）。

BSP 可构建三种镜像：完整固件，或 USB DFU bootloader 与配套应用两个镜像。bootloader 以 USB DFU 设备（"OpenCR App DFU"）接收应用镜像，写入 0x08040000 起的应用区后跳转到应用。应用镜像带有 DFU 运行时接口。

```text
OpenCR1.0.ioc             CubeMX 工程
Core/ Drivers/            CubeMX 生成的初始化代码与 ST HAL / CMSIS
Middlewares/              FreeRTOS、LibXR 子模块
Modules/modules.yaml      使用的模块（`xrobot:` 记录 XRobot 版本）
Modules/sources.yaml      源
xrobot.lock               每个模块使用的提交（lock）
User/app_main.cpp         入口源文件，硬件注册并调用 XROBOT_MAIN()
User/bootloader_main.cpp  DFU bootloader 的入口源文件
User/libxr_config.yaml    LibXR 外设参数，包括数据库（`generator:` 记录 CodeGenerator 版本）
User/xrobot.yaml          配置
STM32F746XX_*.ld          完整固件、bootloader 和应用的链接脚本
cmake/                    工具链文件（含按镜像选择链接脚本的 OPENCR_LINKER_SCRIPT）与 LibXR.CMake（编译设置）
```

`Modules/<owner>/<Repo>/`、`Modules/CMakeLists.txt` 和 `User/xrobot_main.hpp` 由 `xrobot` 生成，已列入 `.gitignore`。

OpenCR 1.0 uses an STM32F746ZGTx and runs FreeRTOS. The terminal is provided over USB CDC (`usb_otg_fs_cdc`). The peripherals are configured in the CubeMX project `OpenCR1.0.ioc`; the `libxr` command generates the entry source `User/app_main.cpp`, which performs the hardware registration with `XR_REGISTER`. The hardware names used in a configuration are these registered names, for example `LED1`, `IMU_CS`, `IMU_INT`, `spi1`, `can2`, `pwm_buzzer`, `database` and `ramfs`. `usb_otg_fs_cdc`, `ramfs` and `pwm_buzzer`, together with the USB DFU runtime and the terminal, are created and registered by hand-written code in the `User Code Begin 3` region, and the rest is generated by the `libxr` command; `USB.usb_otg_fs.enable` in `User/libxr_config.yaml` is false. The database `database` is generated from the `database` setting in `User/libxr_config.yaml` and uses the last Flash sectors 6 and 7 (from 0x08080000).

The BSP builds three images: a full firmware, or a USB DFU bootloader and a matching application as two images. The bootloader appears as a USB DFU device ("OpenCR App DFU"), receives the application image, writes it to the application area starting at 0x08040000 and jumps to it. The application image carries a DFU runtime interface.

`Modules/<owner>/<Repo>/`, `Modules/CMakeLists.txt` and `User/xrobot_main.hpp` are generated by `xrobot` and listed in `.gitignore`.

## 3. 构建 / Build

构建使用 CMake、Ninja 和 `starm-clang`（预设使用 `cmake/starm-clang.cmake`，picolibc 配置）或 `arm-none-eabi-gcc`（`cmake/gcc-arm-none-eabi.cmake`，CI 使用），编译器位于 `PATH` 中。XRobot 为 1.0.0，LibXR CodeGenerator 为 6.0.0，与 `Modules/modules.yaml` 的 `xrobot:` 和 `User/libxr_config.yaml` 的 `generator:` 一致。

```bash
git clone --recursive https://github.com/xrobot-org/BSP-OpenCR-1.0.git
cd BSP-OpenCR-1.0
pip install xrobot==1.0.0 libxr==6.0.0
xrobot setup
cmake --preset Debug
cmake --build --preset Debug
```

`xrobot setup` 拉取模块、检查配置并生成 `User/xrobot_main.hpp`，三种镜像都需要先运行它。CMake 缓存变量 `OPENCR_IMAGE` 选择镜像，产物为 `build/<预设>/OpenCR1.0.elf`：

| `OPENCR_IMAGE` | 入口源文件 | 链接脚本 | 预设 |
| --- | --- | --- | --- |
| `default` | `app_main.cpp` | `STM32F746xx_FLASH.ld`（0x08000000） | `Debug`、`Release`、`GccRelease` |
| `bootloader` | `bootloader_main.cpp` | `STM32F746XX_BOOTLOADER.ld`（0x08000000，128 KiB） | `BootloaderDebug`、`GccBootloaderRelease` |
| `app` | `app_main.cpp` | `STM32F746XX_APP.ld`（0x08040000） | `AppDebug`、`GccAppRelease` |

`Gcc` 开头的预设使用 `cmake/gcc-arm-none-eabi.cmake` 构建 Release 镜像，CI 使用这三个预设。不用预设时：

```bash
cmake . -DCMAKE_TOOLCHAIN_FILE=cmake/gcc-arm-none-eabi.cmake -DCMAKE_BUILD_TYPE=Release -DOPENCR_IMAGE=app -Bbuild -G Ninja
cmake --build build
```

应用代码的优化级别由 `cmake/LibXR.CMake` 开头 “Project settings” 块中的 `LIBXR_OPT_DEBUG`（`-Og`）和 `LIBXR_OPT_RELEASE`（空）设置：`LIBXR_OPT_RELEASE` 为空，Release 构建中应用、`xr` 和 CubeMX 生成的库沿用工具链文件的级别（`starm-clang` 为 `-Oz`，`arm-none-eabi-gcc` 为 `-Os`），Debug 构建中应用使用 `LIBXR_OPT_DEBUG`，`xr` 和这些库使用 `-O2`。`cmake/gcc-arm-none-eabi.cmake` 与 `cmake/starm-clang.cmake` 是 CubeMX 写出的工具链文件，其中按镜像选择链接脚本的 `OPENCR_LINKER_SCRIPT` 是本 BSP 的修改。

构建时 LibXR 检查配置、lock、模块头文件和入口源文件中的硬件注册相对 `User/xrobot_main.hpp` 是否有变化，有变化时构建失败并提示对应的 `xrobot gen -c <配置>`。

在 CubeMX 中修改并重新生成代码后，运行 `libxr stm32 setup` 更新 `User/app_main.cpp`、`User/app_main.h`、`User/flash_map.hpp`、`User/libxr_config.yaml` 和 `cmake/LibXR.CMake`，`User Code` 区域保留。命令说明见 [LibXR_CppCodeGenerator](https://github.com/xrobot-org/LibXR_CppCodeGenerator)。

`.github/workflows/xrobot_stm32.yml` 调用 XRobot 仓库中的共享工作流 `bsp-stm32-ci.yml`，写出工程名 `OpenCR1.0` 和三个预设 `GccRelease`、`GccBootloaderRelease`、`GccAppRelease`。共享工作流在 `ghcr.io/xrobot-org/docker-image-stm32:main` 中安装固定版本的工具，用 `libxr parse` 和 `libxr gen` 重新生成 `User/` 下的四个文件并与提交比对，检查仓库内的文本文件使用 LF 换行，运行 `xrobot format --check` 和 `xrobot setup --frozen`，再用 `arm-none-eabi-gcc` 分别构建 `default`、`bootloader` 和 `app` 三个镜像。`dev` 分支接收修改，`main` 分支由 `dev` 的 PR 更新。

Building uses CMake, Ninja and either `starm-clang` (the presets use `cmake/starm-clang.cmake`, picolibc configuration) or `arm-none-eabi-gcc` (`cmake/gcc-arm-none-eabi.cmake`, used by CI), with the compiler on `PATH`. XRobot is 1.0.0 and the LibXR CodeGenerator is 6.0.0, matching `xrobot:` in `Modules/modules.yaml` and `generator:` in `User/libxr_config.yaml`.

`xrobot setup` fetches the Modules, checks the configurations and generates `User/xrobot_main.hpp`; all three images need it first. The CMake cache variable `OPENCR_IMAGE` selects the image, and the output is `build/<preset>/OpenCR1.0.elf`:

| `OPENCR_IMAGE` | Entry source | Linker script | Presets |
| --- | --- | --- | --- |
| `default` | `app_main.cpp` | `STM32F746xx_FLASH.ld` (0x08000000) | `Debug`, `Release`, `GccRelease` |
| `bootloader` | `bootloader_main.cpp` | `STM32F746XX_BOOTLOADER.ld` (0x08000000, 128 KiB) | `BootloaderDebug`, `GccBootloaderRelease` |
| `app` | `app_main.cpp` | `STM32F746XX_APP.ld` (0x08040000) | `AppDebug`, `GccAppRelease` |

The presets starting with `Gcc` build the Release images with `cmake/gcc-arm-none-eabi.cmake`, and CI uses these three presets. Without presets, use the commands in the second code block above.

The optimization levels of the application code are set by `LIBXR_OPT_DEBUG` (`-Og`) and `LIBXR_OPT_RELEASE` (empty) in the "Project settings" block at the top of `cmake/LibXR.CMake`: with `LIBXR_OPT_RELEASE` empty, Release builds compile the application, `xr` and the libraries generated by CubeMX at the level of the toolchain file (`-Oz` for `starm-clang`, `-Os` for `arm-none-eabi-gcc`), and in Debug builds the application uses `LIBXR_OPT_DEBUG` while `xr` and these libraries use `-O2`. `cmake/gcc-arm-none-eabi.cmake` and `cmake/starm-clang.cmake` are the toolchain files CubeMX wrote, with the per-image linker script selection `OPENCR_LINKER_SCRIPT` as this BSP's modification.

During the build, LibXR checks whether the configurations, the lock, the Module headers and the hardware registrations in the entry source changed relative to `User/xrobot_main.hpp`; on a change the build fails and names the matching `xrobot gen -c <configuration>`.

After changing and regenerating the code in CubeMX, `libxr stm32 setup` updates `User/app_main.cpp`, `User/app_main.h`, `User/flash_map.hpp`, `User/libxr_config.yaml` and `cmake/LibXR.CMake`, and keeps the `User Code` regions. The commands are described in [LibXR_CppCodeGenerator](https://github.com/xrobot-org/LibXR_CppCodeGenerator).

`.github/workflows/xrobot_stm32.yml` calls the shared workflow `bsp-stm32-ci.yml` of the XRobot repository and names the project `OpenCR1.0` and the three presets `GccRelease`, `GccBootloaderRelease` and `GccAppRelease`. The shared workflow installs the pinned tools in `ghcr.io/xrobot-org/docker-image-stm32:main`, regenerates the four files under `User/` with `libxr parse` and `libxr gen` and compares them with the commit, checks that the text files in the repository use LF line endings, runs `xrobot format --check` and `xrobot setup --frozen`, and then builds the `default`, `bootloader` and `app` images with `arm-none-eabi-gcc`. The `dev` branch receives changes and the `main` branch is updated by PRs from `dev`.

## 4. 烧录与运行 / Flash and Run

`default` 镜像和 `bootloader` 镜像按 0x08000000 链接，`app` 镜像按 0x08040000 链接；bootloader 以 USB DFU 设备（"OpenCR App DFU"）接收 `app` 镜像，写入 0x08040000 起的应用区后跳转到应用。运行后通过 USB CDC 连接终端。

bootloader 镜像本身通过 SWD 写入 0x08000000，可使用任意 SWD 调试器。`BootloaderDebug` 预设的产物为 `build/BootloaderDebug/OpenCR1.0.elf`；J-Link Commander 的 `loadbin` 读取二进制文件，因此先用 `objcopy` 转换为 `OpenCR1.0.bin`（`starm-clang` 工具链对应 `starm-objcopy`），再写入芯片：

```bash
cmake --preset BootloaderDebug
cmake --build --preset BootloaderDebug
arm-none-eabi-objcopy -O binary build/BootloaderDebug/OpenCR1.0.elf build/BootloaderDebug/OpenCR1.0.bin
JLink.exe -device STM32F746ZG -if SWD -speed 4000
```

进入 J-Link Commander 后依次输入：

```text
loadbin build/BootloaderDebug/OpenCR1.0.bin 0x08000000
r
g
exit
```

`loadbin` 将镜像写入 0x08000000，`r` 复位芯片，`g` 开始运行。bootloader 运行后，`app` 镜像经 USB DFU 写入。

The `default` and `bootloader` images are linked for 0x08000000 and the `app` image for 0x08040000; the bootloader receives the `app` image as a USB DFU device ("OpenCR App DFU"), writes it to the application area starting at 0x08040000 and jumps to it. At run time the terminal is available over USB CDC.

The bootloader image itself is written over SWD to 0x08000000 with any SWD probe. The `BootloaderDebug` preset produces `build/BootloaderDebug/OpenCR1.0.elf`; `loadbin` in J-Link Commander reads a binary file, so the ELF is first converted to `OpenCR1.0.bin` with `objcopy` (`starm-objcopy` for the `starm-clang` toolchain) and then written to the chip, using the commands in the code blocks above. In J-Link Commander, `loadbin` writes the image to 0x08000000, `r` resets the chip and `g` starts execution. Once the bootloader is running, the `app` image is written over USB DFU.
